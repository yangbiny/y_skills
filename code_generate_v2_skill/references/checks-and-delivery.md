# 变更检查、验证与中文交付

## 生成前与生成后检查

1. 明确语言、入口、调用链、外部依赖、读写类型和批准文件范围。
2. 核对真实 diff：是否保留人工修改；新增/修改/删除是否都有必要；是否意外改格式、生成文件或配置。
3. 按影响检查类型与语法、空值/边界、权限与输入校验、异常和资源释放、异步竞态、幂等及事务。
4. 检查公开 API、DTO、事件、路由、配置、数据库字段、脚本参数、页面行为及所有受影响消费者。
5. Java/Kotlin 服务检查分层、Converter、主库路由与模块目标版本；前端检查字段传递、用户交互及状态同步；其他语言按实际实现检查，不输出不适用的空清单。
6. 检查依赖复用、构建前提、命名、复杂度、重复逻辑与注释。发现批准范围内的缺陷直接修复，不能用报告代替必要修复。

## 验证边界

- 永远不执行单元测试，包括被构建脚本、生命周期、自定义插件或前端脚本间接触发的测试。
- 区分静态阅读、格式/类型检查、编译、打包、浏览器/服务集成和真实数据验证。未执行就明确写未执行。
- 以下只是 Maven 命令模板，必须先核对当前目录、模块、profile、生命周期和插件：`mvn -Dmaven.test.skip=true compile`，或多模块的 `mvn -pl <真实模块> -am -Dmaven.test.skip=true compile`。不要把占位命令说成可直接执行。
- 不默认执行 `test/verify/install/deploy` 或启动服务。不因加了 skip 参数就跳过对自定义执行逻辑的检查。
- 浏览器、接口、数据库、部署或外部写入按现有授权执行，编译批准不自动覆盖这些操作。数据库查询等专项流程不由本包授予权限。
- 构建失败先区分本次问题、已有问题和环境问题。只修批准范围内问题；检查通过后不无理由扩大或重复验证。
- 如生成测试代码，报告“已补充，未执行”；可给人工回归步骤，不将计划当结果。

## 交付格式

按变更规模缩放，简洁中文优先。通常一段概述加以下信息即可，不强制多层标题：

- 变更：文件、关键类/方法、入口和核心数据流；解释必要的层级落点与复用对象。
- 契约：公开接口、业务行为、兼容性、主库路由/事务的变化；没有变化时不重复长篇说明。
- 验证：实际命令或操作及结果，静态分析与运行证据分开。
- 风险与未验证：未编译、未运行单元测试、未连接服务、未验证实际数据等与本次变更有关的缺口。
- 回归点：具体触发条件、操作和预期结果；包括新增行为、旧行为和有关失败分支。
- 后续事项：仅列仍需处理的真实问题。不得把“未发现明显问题”表述为运行验收通过。

需要完整审查报告时可采用“代码预览 / 质量检查 / 风险与未验证项 / 回归项 / 建议”结构。结论需限定证据，如“静态检查未见明显问题，编译通过；运行行为未验证”。明确的编译失败、契约破坏、严重逻辑错误或必要信息缺失才标记阻塞。
