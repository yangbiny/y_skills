# 变更检查、验证与中文交付

## 生成前与生成后检查

1. 明确语言、入口、调用链、外部依赖、读写类型和批准文件范围。
2. 核对真实 diff：是否保留人工修改；新增/修改/删除是否都有必要；是否意外改格式、生成文件或配置。
3. 按影响检查类型与语法、空值/边界、权限与输入校验、异常和资源释放、异步竞态、幂等及事务。
4. 检查公开 API、DTO、事件、路由、配置、数据库字段、脚本参数、页面行为及所有受影响消费者。
5. Java/Kotlin 服务检查分层、Converter、主库路由与模块目标版本；前端检查字段传递、用户交互及状态同步；其他语言按实际实现检查，不输出不适用的空清单。
6. 检查依赖复用、构建前提、命名、复杂度、重复逻辑与注释。发现批准范围内的缺陷直接修复，不能用报告代替必要修复。

## 验证边界

- 永远不执行单元测试，包括被构建脚本、生命周期、自定义插件、前端脚本或 Git hooks 间接触发的测试。提交推送授权不等于解除这条限制；遇到冲突先完成其他可执行检查，再说明阻塞，不擅自绕过 hook。
- 区分静态阅读、格式/类型检查、编译、打包、浏览器/服务集成和真实数据验证。未执行就明确写未执行。
- 以下只是 Maven 命令模板，必须先核对当前目录、模块、profile、生命周期和插件：`mvn -Dmaven.test.skip=true compile`，或多模块的 `mvn -pl <真实模块> -am -Dmaven.test.skip=true compile`。不要把占位命令说成可直接执行。
- 未获授权时不默认执行 `test/verify/install/deploy` 或启动服务；`dt-metadata` 的 SNAPSHOT deploy 已获长期授权，按 [版本与发布规则](project-conventions.md#dt-metadata-版本与-snapshot-发布) 完成，不重复请求发布批准。deploy 会经过前序 Maven 生命周期，仍须核验插件和单测跳过配置。
- 浏览器、接口、数据库、部署或外部写入按现有授权执行，编译批准不自动覆盖这些操作。数据库查询等专项流程不由本包授予权限。
- 构建失败先区分本次问题、已有问题和环境问题。只修批准范围内问题；检查通过后不无理由扩大或重复验证。
- 如生成测试代码，报告“已补充，未执行”；可给人工回归步骤，不将计划当结果。测试源码编译和测试执行分别记录：需要测试编译时核验 `test-compile` 的实际覆盖，不能以 `maven.test.skip=true` 跳过后的成功声称测试编译通过。

## 前端提交前检查

对 `dtw-guide` 和 `hasaki` 必须读取 [前端验证与推送](frontend-push-checks.md)，依次确认：

1. 项目工具与依赖可用，真实分支、暂存范围及钩子已检查。
2. 改动文件的格式/静态检查、源码类型检查与测试文件类型覆盖已分别确认。测试未纳入配置或未覆盖 Vue/JS 转换链时明确报告，不能写“单测编译全部通过”。
3. 相关目标环境构建和项目专项检查完成。失败区分新增缺陷、已有基线问题和环境阻塞；没有本次可比证据不得归为历史问题。
4. 必需检查失败、缺失，或钩子将执行被禁止的单测时停止提交推送，不把长期授权当作豁免。若用户明确接受某项已知风险，记录接受范围，不能把失败改报通过。
5. hook 修改文件后检查最终 diff，并重新验证受影响部分；只有提交成功才允许推送，最终报告本地提交与远端结果。

## 交付格式

按变更规模缩放，简洁中文优先。通常一段概述加以下信息即可，不强制多层标题：

- 变更：文件、关键类/方法、入口和核心数据流；解释必要的层级落点与复用对象。
- 契约：公开接口、业务行为、兼容性、主库路由/事务的变化；没有变化时不重复长篇说明。
- 验证：实际命令或操作及结果，静态分析与运行证据分开。前端单列格式/静态检查、源码类型、测试文件类型覆盖、环境构建、单测执行和浏览器验收；提交推送发生时附分支、提交 SHA、远端及 CI 已知状态。
- Maven 发布：对 `dt-metadata` 记录原版本、新版本、实际发布坐标/模块、目标仓库标识、deploy 结果及远程确认情况；本地 install 不等于远程 deploy，远程制品发布不等于 Git 推送或消费者已更新。
- 风险与未验证：未编译、未运行单元测试、未连接服务、未验证实际数据等与本次变更有关的缺口。
- 回归点：具体触发条件、操作和预期结果；包括新增行为、旧行为和有关失败分支。
- 后续事项：仅列仍需处理的真实问题。不得把“未发现明显问题”表述为运行验收通过。

需要完整审查报告时可采用“代码预览 / 质量检查 / 风险与未验证项 / 回归项 / 建议”结构。结论需限定证据，如“静态检查未见明显问题，编译通过；运行行为未验证”。明确的编译失败、契约破坏、严重逻辑错误或必要信息缺失才标记阻塞。
