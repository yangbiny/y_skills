# PRD 与技术方案模式

用户要求文档时启用；普通局部修复不强制先写 PRD 或长篇方案。

## 输出约定

- 默认在聊天返回 Markdown 正文，不自动创建文件。用户明确要求落盘并已批准内容范围时，优先指定位置；未指定时用当前工作区 `docs/`，遵守写入权限。
- 根据需求提炼标题，文件名分别为 `<标题>_PRD.md`、`<标题>_solution.md`，不得把标题直接当含任意路径的文件名。
- 独立文档正文第一行使用 `文件名：<实际文件名>`；不额外添加无关前言。用户要求其他格式时按其要求。
- 按对应模板的章节顺序和意图撰写；用户指定模板时优先用户模板。不适用部分简短注明，不编造数据模型、埋点或系统。
- 不确定信息明确记入待确认项；可据上下文提出带标签的假设，影响业务契约或实施的关键缺口不能伪装成已定结论。
- 有实质流程、分支或状态流转时用简洁 Mermaid；单步动作不机械配图。

## PRD

读取 [PRD 模板](prd_template.md)。写清原始输入、背景、核心规则、各功能触发条件、正常/异常流程及下游影响。数据字段给出含义、取值和约束；埋点只在需求涉及时说明事件、属性、触发时机和用途。验收点具体且可观察，未知边界集中在其他说明。

## 技术方案

读取 [技术方案模板](solution_template.md)。形成可独立指导实现的方案：范围、成功标准、现状、入口、处理流程、状态变化、异常分支、幂等/并发/事务、接口与数据兼容、代码落点和任务依赖。

- 代码落点尽可能到仓库、模块、类、方法、文件；尚未定位的名称标为拟定。
- 任务拆解给出产出和完成标准，不默认创建子任务或触发外部工具。
- 区分测试设计和实际执行；单元测试章节只列设计/待补代码，并注明禁止执行。
- 文档完成不代表获准实现、修改数据库或发布。
