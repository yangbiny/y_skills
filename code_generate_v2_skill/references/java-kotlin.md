# Java / Kotlin 风格与兼容性

## 通用选择

- 先读适用的 `.editorconfig`、构建配置、格式化规则与同模块代码。采用项目有效设置，不把 IntelliJ 仓库的缩进、括号或工具类规则当作所有项目的默认值。
- 保持已有文件语言。新增文件遵循模块主流语言；Kotlin 项目优先 Kotlin，用户指定 Java 时使用 Java，不为风格切换语言。
- 先核实模块实际 Java release/API target、Kotlin 版本和 JVM target，包括父配置；本机安装的 JDK 不代表项目兼容级别。不要擅自升级语言级别或启用 preview。
- 不重排或格式化无关文件，不用更“现代”的写法改变行为。

## Kotlin

- 优先 `val`、明确空值语义和数据承载用的 `data class`；有身份语义或生命周期的领域实体不要机械改成 data class。
- 扩展函数适合自然附着于接收者的通用操作。DTO 转换优先复用已有 Converter；只有一处使用时不要为扩展语法新建文件或隐式依赖。
- `when` 处理封闭层次时尽可能穷尽合法分支；不要为消除编译提示加入会吞掉新枚举值的 `else`。普通判等或单分支判断按含义选择，不一概禁止。
- 合并多个子类型分支前打开类型定义，只有共同父类型恰好覆盖目标集合时才替换，避免无意扩大匹配范围。
- 协程与异步逻辑保留取消传播、作用域所有权、调度器和资源释放。不吞掉取消异常；IntelliJ 的具体处理方式见 [项目约定](project-conventions.md)。

## Java

使用新语法或替换 API 前阅读 [Modern Java](modern-java.md)，重点核对：

- `var` 的类型推导、基本类型宽度、重载选择；字段、参数、返回值保持明确类型。
- record 的相等性、访问器、序列化、反射和继承契约；封闭层次不关闭已有扩展点。
- switch 的空值与 fall-through 行为；文本块的空白与末尾换行。
- 集合是否允许修改、空元素、重复键/元素、迭代顺序，以及快照和视图的差别。
- 不因运行时支持就替换线程模型；保留既有执行器、锁、取消和生命周期。

## 可维护性

- 类职责清晰，避免深继承和过度抽象。能直接表达的逻辑不提取成公有工具方法。
- 校验、状态变化、错误语义清楚即可，不强制为每行调用加注释或每一项校验建方法。
- 不以风格清理为由改变接口、构造约定、可变性或事务行为。
