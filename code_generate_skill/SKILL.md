# 通用代码预览报告技能

## 目标

在完成代码生成、补全、迁移或重构后，必须对生成结果进行一次面向交付的代码预览，并用中文输出结构化报告。报告要帮助用户快速判断本次代码是否可读、可维护、符合项目约束，以及还存在哪些未验证风险。

## 使用流程

1. 先确认本次生成或修改涉及的文件、语言、入口方法、核心调用链和外部依赖。
2. 对新增或修改代码进行预览，说明主要逻辑、关键分支、数据流和接口变化。
3. 按目标语言和项目上下文检查类型、语法、接口契约、错误处理、边界条件、并发或异步逻辑、依赖使用、安全性和可维护性。
4. 如果已运行编译、测试、格式化、静态检查或页面预览，必须准确说明命令和结果。
5. 如果没有运行验证，必须明确写入未验证项，不得暗示或虚构验证通过。
6. 如发现明显问题，先给出可执行修改建议，再给出结论。
7. 新变更的，需要给出代码测试回归项

## 预览重点

- 变更范围：新增、修改、删除的文件，以及每个文件承担的职责。
- 关键代码：主要入口、核心方法、核心组件、关键 SQL、关键样式或关键脚本。
- 接口影响：公开 API、函数签名、DTO、事件、路由、配置、数据库结构、命令参数或页面交互是否变化。
- 运行风险：编译错误、类型错误、空值、越界、资源泄露、异常吞掉、异步竞态、事务边界、权限校验、输入校验。
- 依赖风险：是否引入新依赖，是否复用项目已有工具，是否改变构建、运行或部署前提。
- 可维护性：命名、复杂度、重复代码、分层边界、注释必要性、与既有风格是否一致。

## 报告格式

每次报告必须使用中文，并按以下结构输出：

```markdown
## 代码预览

- 变更文件：
- 主要入口：
- 核心逻辑：

## 质量检查

- 语言与语法：
- 接口与契约：
- 错误处理：
- 边界条件：
- 依赖与集成：
- 可维护性：

## 风险与未验证项

- 已验证：
- 未验证：
- 主要风险：

## 测试注意项
- 回归项：
- 新增项：


## 修改建议

- 建议：

## 结论

结论：通过 / 需调整 / 阻塞
```

## 结论判定

- `通过`：代码结构清晰，未发现明显问题，已验证或未验证风险较低。
- `需调整`：存在可修复问题或重要未验证项，但不阻塞继续迭代。
- `阻塞`：存在编译失败、契约破坏、严重逻辑错误、安全风险、数据破坏风险，或缺少完成需求所必需的信息。

## 注意事项

- 不要把报告写成泛泛总结，必须对应实际生成的代码。
- 不要省略未验证项，尤其是未运行测试、未编译、未打开页面、未连接数据库、未验证兼容性等情况。
- 不要为了报告格式强行夸大问题；没有问题时直接说明未发现明显问题。
- 当用户或仓库规则禁止运行某类验证时，必须遵守限制，并在报告中说明。
