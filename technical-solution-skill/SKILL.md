# 技术方案 Skill

## 工作流

1. 起草前先读取 `references/solution_template.md`。
2. 从用户输入中提炼简洁标题，并作为文件名提示：`<title>_solution.md`。
3. 严格遵循 `references/solution_template.md` 的章节顺序和表达意图。
4. 输出内容应以“可直接指导编码实现的技术方案”为中心，重点描述范围、改造点、功能实现、系统交互、数据模型影响、代码落点、任务拆解和测试要求。
5. 涉及流程、状态流转或分支判断时，使用 Mermaid 流程图，图示保持精简，并且必须直接服务于方案说明。
6. 如果输入信息不完整，优先基于上下文做合理假设，并将假设记录在 `风险与待确认项` 中；只有在缺失信息会阻塞方案输出时才追问。
7. 仅输出 Markdown 正文，不要在文档外附加解释、前言或额外说明。
8. 文档必须以如下内容开头：

```text
文件名：<title>_solution.md
```

## 内容规则

- 除非用户明确要求其他语言，标题和正文一律使用中文。
- 方案必须自包含，明确原始输入、目标、范围、非范围和成功标准，避免依赖人工补充上下文。
- 优先描述具体系统行为、模块职责和实现路径，避免空泛的产品化表述。
- `详细实现` 部分按功能拆分，分别说明入口、触发条件、处理流程、异常分支、状态变化、事务边界以及上下游影响。
- `代码落点` 部分必须尽量明确到模块、层级、类、文件或目录，说明改动类型和职责。
- `接口设计` 与 `数据模型与存储变更` 需要列出字段、含义、取值范围、约束条件、兼容性要求以及新增/变更点。
- `任务拆解` 必须能够直接分派执行，包含任务目标、依赖、产出物和完成标准。
- `测试与验收` 必须具体到可执行测试点，不允许只写笼统描述。
- 对不确定、待确认或存在实现边界的内容，统一放入 `风险与待确认项`，并明确其影响。

## 文件输出

- 默认行为是返回 Markdown 内容，不强制写入文件。
- 如用户明确要求落盘，只允许写入当前工作区内的 `./docs/<title>_solution.md`。
- 不允许写入当前工作区之外的任何路径。
