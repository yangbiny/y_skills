# Java 开发工作流

全程使用中文，保持简洁。遵守当前项目的 AGENTS.md。
不得执行单元测试，不得擅自扩大修改范围。

## 1. 分析

只进行读取和分析，不修改文件。

- 阅读当前项目约定和相关实现。
- 根据项目规则选择 CodeGraph、MCP 或代码检索工具。
- 功能开发：说明现有实现和涉及的模块。
- Bug 修复：说明原因及关键调用链。
- 重构：明确需要保持的行为和接口契约。
- 给出相关类名、方法名和文件路径。

## 2. 提出方案

列出：

- 准备新增或修改的文件。
- 每个文件的修改内容及原因。
- 对接口和业务行为的影响。
- 验证方式及拟执行的构建命令。

方案默认在聊天中展示，不擅自生成方案文件。

## 3. 等待批准

修改文件前，必须获得用户对具体修改范围的批准。

- 当前会话已有批准且覆盖本次修改时，继续执行。
- 缺少批准时，提交方案并结束当前回复，等待用户。
- 不得把沉默、工具放行或自己生成的记录视为用户批准。
- 需要扩大范围时，说明新增修改并重新获得批准。

## 4. 实现

仅修改已批准的内容。

- 遵循项目现有代码风格和 DDD 分层。
- 保持接口契约，避免不必要的依赖和抽象。
- Facade 写操作使用 databases.withPrimary 包裹。
- 可用且适用时使用 java-generate-skill、code-generate-skill。
- 核心逻辑按项目要求补充测试代码，但不得运行测试。

## 5. 检查与编译

- 检查变更、分层、接口和主库写入包装。
- 执行构建前，核验 Maven 配置不会运行单元测试。
- 只执行已授权、符合项目规则的编译操作。
- 构建输出直接返回，不在仓库根目录生成日志。
- 编译失败时说明原因；修复不得超出已批准范围。
- 适用时使用 code-generate-preview-skill 输出中文预览。

## 6. 交付

简洁说明：

- 修改了什么，以及为什么修改。
- 关键文件、类和方法。
- 实际执行的验证及结果。
- 未验证部分和仍需处理的问题。
- dtw-guide 在确认分支后，可以 直接提交并推送变动到远程仓库中，并报告：变更已推送远程仓库。提交信息在分支上需要满足：[it reboot]变更内容[from codex]

不得把未执行的检查描述为通过。
